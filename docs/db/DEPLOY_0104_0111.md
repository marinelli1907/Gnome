## Apply order

0104 → 0105 → 0106 → 0107 → 0108 → 0109 → 0110 → 0111, one `apply_migration` each, in order,
NOTHING piecemeal in between. Each file is idempotent and was proven to apply against a database
one step behind, so a mid-sequence failure leaves a resumable state, not a torn one.

After 0106 applies, one data fix is required before FOUNDING3 is redeemable:

promo_validate answers NOT_CONFIGURED until it is set.)

Then deploy, in order: `billing-checkout`, `stripe-webhook` (both reference 0106/0107 RPCs — they
must NOT be deployed before the migrations), then web (`web/deploy/deploy.sh`, which snapshots
`/var/www/gnome-web` to `gnome-web.bak-<ts>` first).

## What the apply changes for EXISTING data

- `listings.listing_type` DEFAULT flips to `'sale'` — no stored row changes; both clients always
  send the type explicitly.
- The active-listing cap trigger is dropped and the publish-allowance trigger installed. Existing
  ACTIVE listings are untouched; the ledger starts empty, so every seller starts the current
  period with full allowance. Nobody loses a listing; nobody is charged anything retroactively.
- `plan_limits` gains the 0104 columns and the display names. Enum values do not change.
- New tables (`promotion_*`, `listing_publish_*`, `market_qr*`) start empty.

## Rollback

Application rollback: web redeploys from the `gnome-web.bak-<ts>` snapshot (copy back, pm2
restart, no rebuild); edge functions redeploy from `main` (`1766529`) sources.

Database rollback is DELIBERATELY not a script that drops the new objects blindly:
- 0104's retired trigger function `enforce_plan_limit()` is left defined — re-attaching the old
  cap is one `CREATE TRIGGER listings_enforce_plan_limit …` away.
- New tables can be left in place harmlessly (nothing on `main` reads them); dropping them is only
  needed if a re-run of the forward migrations is intended.
- The `listing_type` default reverts with one `ALTER TABLE … SET DEFAULT 'free'`.
- Money safety: authorizations/redemptions are additive ledgers keyed on Stripe ids — rollback
  never deletes payment records.

## Fixtures policy

End-to-end verification creates QA users/markets. Every fixture id is recorded in the deploy log
and deleted afterwards; prior rounds left QA residue that had to be chased later, so cleanup is
part of the checklist, not an afterthought.
